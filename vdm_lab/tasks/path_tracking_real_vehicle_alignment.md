# VDM 路径跟踪实验与实车对接方案

**用途：** 供助教、课程团队、算法实现人员和实车负责人在上车前对齐实验范围、软件接口、数据口径、安全门槛和责任分工。

**本次希望确认的结论：** 我们将完成 PP、运动学 LQR、MPC 三种算法在不同路径和速度下的消融；仿真评测框架和实车日志模板已准备好。开始自动控制前，需要实车侧确认实际启用的配置、ROS 接口、单位、场地安全流程，并明确 MPC 的实车接入方案和负责人。

> 本文不替代现场安全规程。车辆参数、限幅、速度上限与允许路线均以现场负责人确认的实际配置为准。

## 2. 目标和实验边界

课程要求为：三个算法、不同路径、不同速度的消融，并比较时间、精度和可视化结果。时间必须拆成两类，不能混用：

- **车辆完成用时**：从自动控制有效开始到到达终点的实际任务时间；
- **控制计算耗时**：每个控制周期内控制器求解命令所花的时间。

| 维度 | 仿真统一方案 | 实车执行方案 |
| --- | --- | --- |
| 算法 | PP、运动学 LQR、线性 MPC | PP、LQR 可按课程接口接入；MPC 需完成 ROS C++ 接入，或先确认一个等价且可运行的接口方案。 |
| 路径 | 双移线、直角转弯、S 弯 | 按场地安全边界选择与三类形态一致的路线，保留参考轨迹文件及版本号。 |
| 速度 | `low`、`medium`、`high` 三档 | 课程建议先用 5 km/h、10 km/h；第三档由实车负责人按场地和车辆状态确认。 |
| 重复次数 | 每组合至少一次基线运行 | 每个有效组合建议至少 3 次；失败与人工接管运行必须保留。 |
| 组合数量 | 3 算法 × 3 路径 × 3 速度 = 27 组 | 若实车只允许 2 个安全速度档，则为 18 组；重复次数另计。 |

## 3. 控制与数据接口需要对齐的内容

仿真侧的控制器输入为车辆状态和参考路径，输出为纵向命令与前轮转角。实车侧需要把相同控制逻辑映射到 ROS 消息和底盘接口，并证明命令确实下发、车辆确实响应。

| 环节 | 需要确认的输入输出 | 对接方需要提供的内容 |
| --- | --- | --- |
| 状态输入 | 位置、航向、车速、时间戳、坐标系 | 实际 topic 名称、消息类型、频率、坐标系定义、定位来源与时间基准。 |
| 参考路径 | 路径点、航向、曲率、目标速度 | 发布 topic 或文件格式；路径版本号、起终点和路径坐标系。 |
| 控制输出 | 期望速度、减速度、前轮转角 | `TrackerResult` 或实际消息字段、单位、正负方向、饱和范围。 |
| 底盘反馈 | 下发命令、实际速度、实际转角、控制模式 | CAN 或底盘反馈 topic；确认是否可记录实际响应。 |
| 安全状态 | 手动、自动、急停、人工接管 | 模式字段、触发条件、操作员记录方式和场地规则。 |

### 3.1 单位和方向是上车前的硬门槛

- 仿真默认采用 **m/s** 和 **rad**；课程 ROS C++ 工程中常见速度为 **km/h**、转角为 **deg**。
- 在第一次自动控制前，要通过一条静态或极低速样例命令同时验证：数值量级、转向左右方向、速度正负方向、实际反馈是否一致。
- 不允许仅依据字段名称推测单位；必须在日志中留下样例值和确认人。

## 4. 统一数据口径与验收指标

每次仿真或实车运行都应有唯一的 `experiment.yaml`，并保留原始 rosbag 与由 rosbag 导出的统一 `tracking.csv`。推荐命名方式：

```text
{algorithm}_{route}_{speed}_{date}_run{index}
例如：pp_s_curve_5kmh_20260917_run01
```

| 记录对象 | 最小字段 | 口径要求 |
| --- | --- | --- |
| `experiment.yaml` | 实验标识、算法版本、路径版本、速度档、参数文件、控制周期、操作员、场地 | 每次运行独立保存，不能事后覆盖。 |
| `tracking.csv` | 时间、位置、航向、实际速度、目标速度、实际或命令转角、横向误差、控制模式、接管标记 | 统一使用 s、m、rad、m/s；同时写明原始单位和转换方式。 |
| rosbag | 状态、路径、控制命令、底盘反馈、控制模式、急停或接管事件 | 保留完整 topic 名称、开始结束时间和时间基准。 |
| 失败记录 | 失败时刻、原因、现象、人工动作、安全影响 | 失败和人工接管不能静默删除，要在汇总表单列。 |

| 指标类别 | 指标 | 说明 |
| --- | --- | --- |
| 精度 | MAE、RMSE、P95 横向误差、最大横向误差 | 横向误差单位统一为 m；统计窗口应只覆盖自动控制有效时段。 |
| 时间 | 完成用时、控制计算平均值、P95、最大值 | 前者衡量任务效率，后者衡量实时性；必须分开报告。 |
| 平稳性 | 平均和最大转向速率、平均和最大加速度 | 观察命令抖动、舒适性和执行器约束。 |
| 有效性与安全 | 到达终点、有效运行数、失败次数、人工接管次数 | 在结论中说明样本量；未到达终点不能按“完成用时”参与排名。 |

## 5. 需要提交或展示的可视化

1. 每个代表性运行的参考轨迹与实际轨迹叠图，标出起点、终点和人工接管点。
2. 每个代表性运行的横向误差、车速、转角随时间曲线；控制模式和接管事件应能与时间轴对应。
3. 算法 × 路径 × 速度的 MAE、RMSE、完成用时、控制计算耗时热力图或分组柱状图。
4. 仿真与实车在同一算法、相近路径形态和相同速度档下的并列表，并对差异作出可追溯解释。
5. 每种算法至少保留一个成功案例和一个偏差明显或发生接管的案例，不只展示最佳结果。

## 6. 仿真执行计划

仿真不需要一次性跑完 27 组。应先确认环境和单组输出正常，再批量运行，最后汇总。

| 阶段 | 执行内容 | 完成判据 |
| --- | --- | --- |
| 环境检查 | 安装 `requirements.txt`，确认可导入 `cvxpy`、`matplotlib`、`numpy`。 | MPC 可以初始化，项目测试通过。 |
| 单组冒烟 | PP、LQR 各选一组，在目标控制周期下输出日志与图。 | 可到达终点；指标、图和运行元数据齐全。 |
| 全量消融 | 运行 27 组组合，异常组照常保留。 | 有单次目录、CSV 汇总和指标热力图。 |
| 复核 | 核对路径、速度、控制周期确实变化；检查异常曲线。 | 结论只基于有效样本，并说明失败与缺失。 |

当前已验证 PP 与 LQR 的 30 Hz 单组运行和汇总流程。完整 MPC 消融仍依赖本机安装 `cvxpy` 后复跑，因此不能将 MPC 的最终比较结果写成已完成。

## 7. 上车前门槛与执行顺序

实车第一目标不是立即完成完整消融，而是证明状态、参考、命令和底盘反馈可以在同一时间轴、同一单位体系下闭环对应。

| 顺序 | 执行内容 | 进入下一步的条件 |
| --- | --- | --- |
| 1 接口回放 | 只采集 rosbag，不开启自动控制；核验状态、路径与底盘反馈。 | topic、消息频率、坐标系、时间戳已确认。 |
| 2 静态命令 | 按场地规定以小幅测试值验证速度和转角的单位与正负方向。 | 命令量级与实际响应一致，无异常模式切换。 |
| 3 低速直线 | PP 先行，在短直线低速自动控制并完整录包。 | 急停和人工接管可用，横向与纵向响应可解释。 |
| 4 单算法曲线路径 | 逐步测试 LQR，再测试已接入的 MPC。 | 每次运行都有 YAML、bag、CSV 和现场日志。 |
| 5 完整消融 | 按路径和速度矩阵开展重复运行。 | 前四步持续稳定，实车负责人放行对应速度与路线。 |

## 8. 下一步

在确认实际配置、ROS 接口、单位与现场安全流程后，可以并行推进两件事：

1. 在仿真环境补齐 `cvxpy` 后完成 27 组消融并生成统一汇总；
2. 在实车上先做接口回放与低速直线验证，确认后再进入曲线路径和完整矩阵。

只有完成第 7 节前三级验证后，才申请进入完整实车消融。这样得到的时间、精度和可视化结果才具备可比性和可解释性。
